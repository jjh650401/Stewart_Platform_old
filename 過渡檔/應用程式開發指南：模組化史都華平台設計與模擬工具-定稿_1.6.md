### **第三章：變數與參數定義**

本章定義了應用程式中使用的所有關鍵變數，作為唯一的參考標準。

  * **GUI 與核心引擎單位約定**:
      * **GUI 層**: 為了符合使用者習慣，所有在圖形介面 (`GeometryWidget`, `DynamicsWidget`) 的輸入框中，長度單位皆為 **毫米 (mm)**。
      * **核心引擎層 (`CoreEngine`)**: 為了符合科學計算標準，所有內部計算與參數儲存，長度單位皆為 **米 (m)**。
      * **資料流**: GUI 層在將參數傳遞給核心引擎前，負責將 `mm` 轉換為 `m`。核心引擎回傳計算結果時，GUI 層負責將 `m` 轉換回 `mm` 進行顯示。
      * **[新增]** **加速度單位**: GUI 層為了方便使用者輸入，線性加速度單位使用**重力加速度 (g)**。在將參數傳遞給核心引擎前，GUI 層負責將 `g` 值乘以 `9.81` 轉換為核心引擎所使用的 `m/s²` 單位。
  * **幾何參數**:
      * $R_a$ (m): 下平台節點圓的半徑。
      * $R_b$ (m): 上平台節點圓的半徑。
      * **[修改]** $H$ (m): **自然平衡零位高度 (Natural Balance Zero Position Height)**。此為一個**計算結果**，定義為當所有電動缸長度均處於其**可用行程中點** ($L + s_{buffer}/2 + s/2$) 時，平台在保持水平姿態下的高度。它是所有姿態控制和工作空間分析的**操作基準零點**。
      * **[修改]** $h$ (m): **平台初始高度 (Initial Height)**。此為一個理論上的物理量，定義為當所有電動缸長度均處於其**最小機械長度** ($L$) 時，平台在保持水平姿態下的高度。它代表了平台的**物理下限**，對應總機械行程的起點。
      * **[新增]** **開發者註記：`H` 與 `h` 的區別**
          > `H` 是軟體中所有相對運動的**參考原點**，旨在最大化和對稱化可用工作空間。而 `h` 則代表平台的**物理最低點**。兩者在概念上和數值上均不相同，請務必加以區分。
      * **自然零位偏移** $(T_{x0}, T_{y0})$ (m): 與 $H$ 同時解算出的，在自然平衡零位下的水平面偏移量。
      * **六自由度平台**:
          * $D_f$ (m): 下平台相鄰節點間的較大弦長。
          * $d_f$ (m): 下平台相鄰節點間的較小弦長。
          * $D_m$ (m): 上平台相鄰節點間的較大弦長。
          * $d_m$ (m): 上平台相鄰節點間的較小弦長。
      * **[新增]** **相位角** $\Delta\theta$ (rad 或 deg): **相位角 (Phase Angle)**，亦可稱為 **交錯角 (Stagger Angle)** 或 **扭轉角 (Twist Angle)**。
          *   **定義**: 在平台的初始零位姿態下，從 Z 軸俯視，上平台節點 $B_i$ 的方位角與下平台對應節點 $A_i$ 的方位角之間的夾角。
          *   **性質**: 這是一個由上下平台四個弦長 ($D_f, d_f, D_m, d_m$) 決定的**內建幾何特性**，而非可動的姿態參數。
          *   **意義**: 此參數對於**避免奇異點 (Singularity)**、**優化工作空間形狀**以及改善力傳遞特性至關重要。
  * **電動缸參數**:
      * $L$ (m): 電動缸的固定最小長度。
      * $s$ (m): 電動缸的**可用行程 (Usable Stroke)** (使用者**輸入**)。
      * $s_{buffer}$ (m): 電動缸兩端預留的**安全裕量 (Safety Buffer)** 總和 (使用者**輸入**)。
      * $s_{mech}$ (m): 電動缸的**總機械行程 (Total Mechanical Stroke)** (由程式**計算**，$s_{mech} = s + s_{buffer}$)。
      * $l_i$ (m): 第 $i$ 根電動缸的當前長度。其安全運動範圍為 $[L + s_{buffer}/2, L + s_{buffer}/2 + s]$。
  * **視角參數 (View Parameters)**:
      * `view_params` (dict): 一個包含攝影機所有狀態的字典集合，用於儲存和恢復 3D 視圖。
      * `cpos` (list): 一個列表，包含三個核心向量 `[position, focal_point, view_up]`，定義了攝影機的方位。
      * `parallel_scale` (float): 一個數值，定義了攝影機的縮放等級或遠近。
  * **平台自由度與性能**:
      * $T_x, T_y, T_z$ (m): 沿 X, Y, Z 軸的最大平移範圍。
      * $\alpha, \beta, \gamma$ (rad 或 deg): 繞 X, Y, Z 軸的最大旋轉範圍 (Roll, Pitch, Yaw)。
      * $v_{max}, a_{max}$ (m/s, m/s²): 平台的最大線速度與線加速度。
  * **驅動系統參數**:
      * $P_h$ (m/rev): 螺桿導程 (Pitch)。
      * $N_1$: 傳動端（馬達端）皮帶輪的齒數。
      * $N_2$: 從動端（螺桿端）皮帶輪的齒數。
      * $i$: 減速比，$i = N_2 / N_1$。
      * $\eta_s$: 螺桿傳動效率。
      * $\eta_b$: 皮帶輪傳動效率。
      * $F_{rated}$ (N): 每根電動缸的額定最大軸向出力。
      * $\tau_{motor}$ (N·m): 馬達的額定扭力。
      * $n_{motor}$ (rev/s): 馬達的額定轉速。
  * **[修改]動力學參數**:
      * `platform_mass` (kg): 上平台本身的質量。
      * `load_mass` (kg): 附加於上平台的負載質量。
      * `load_com_x`, `load_com_y`, `load_com_z` (m): 負載質心 (Center of Mass) 相對於上平台幾何中心的位置向量。
      * `lin_accel` (m/s²): 平台期望的線性加速度 (Linear Acceleration) 向量 `[ax, ay, az]`。
      * `ang_accel` (rad/s²): 平台期望的角加速度 (Angular Acceleration) 向量 `[αx, αy, αz]`。
      * $\mathbf{I}$ (kg·m²): 平台與負載的轉動慣量張量。
      * $g$ (m/s²): 重力加速度，預設為 9.81。

#### **4.2 運動學與動力學公式**

1.  **向量定義**:  
    $\mathbf{l}_i = (\mathbf{T} + \mathbf{R}\mathbf{B}_i^0) - \mathbf{A}_i$

2.  **逆向運動學 (Inverse Kinematics, IK)**:  
    $l_i = ||(\mathbf{T} + \mathbf{R}\mathbf{B}_i^0) - \mathbf{A}_i||$

3.  **正向運動學 (Forward Kinematics, FK)**:  
    求解 $||\mathbf{l}_i||^2 - l_{i, \text{given}}^2 = 0$

4.  **[新增]** **逆動力學 (Inverse Dynamics)**:
    *   **目標**: 求解各致動器 (電動缸) 所需的瞬時力 $F_{actuators}$。
    *   **核心方程式**:  
        $F_{actuators} = (\mathbf{J}^{-1})^T \cdot \mathbf{W}_{ext}$
    *   其中 $\mathbf{J}$ 是平台的**雅可比矩陣 (Jacobian Matrix)**，$\mathbf{W}_{ext}$ 是施加在平台的總外力/力矩向量 **(Wrench)**，它由重力與慣性力/力矩組成。
    *   **[修改]** **開發者註記**:  
        `dynamics_engine.py` 中的模型為簡化模型，主要考慮重力與達朗貝爾慣性力，暫未包含高速旋轉下顯著的科里奧利力與向心力。  
        **此外，目前的轉動慣量張量 ($\mathbf{I}$) 採用了一個固定的近似值 (`np.eye(3) * 0.1`)，並未根據平台和負載的實際幾何進行計算，此設計會影響高速轉動下的力矩計算精度，為未來版本的待改進項。**

### **第六章：開發者註記與決策記錄**

**[新增]** (本章節已完全重寫，以記錄從 v1.5 到 v1.6 的完整除錯與決策過程)

本章旨在記錄在達成 v1.6 穩定基線的過程中，所遇到的關鍵挑戰、錯誤分析以及最終的解決方案。這份記錄是未來維護與功能迭代的寶貴資產，旨在避免重蹈覆轍。

*   **[新增]** **6.1 迭代修正一：物理模型與方位定義的標準化**
    *   **主題**：確保軟體的計算、顯示與物理現實完全一致。
    *   **遇到的问题与决策记录**：
        1.  **行程定義偏差**：初版對「可用行程」的定義忽略了 `s_buffer`，導致工作空間分析不準確。
        2.  **方位定義顛倒**：初版六自由度平台的初始方位與設計示意圖顛倒 180 度，是導致旋轉方向混亂的根源。
        3.  **旋转直觉不符**：在方位修正後，純數學的「右手定則」旋轉方向與模擬器操作員的直覺（如 `+Pitch`=抬頭）不符。
        4.  **3-DOF 旋转模型错误**：初版三自由度平台的旋轉是圍繞「外接圓圓心」而非「幾何中心」，導致動作異常。
    *   **最終方案：**：
        1.  **明確物理模型**：在第三章中，以圖文方式明確電動缸行程的物理分佈，並以此為基准，重寫了 `kinematics.py` 中所有相關的計算邏輯（`H` 高度，工作空間分析）。
        2.  **強制標準方位**：在 `kinematics.py` 中，透過增加 180 度旋轉偏移，強制使六自由度平台的初始方位與第四章新增的「標準方位示意圖」對齊。
        3.  **前端體驗適配**：在 `main_window.py` 的 `update_3d_view` 函式中，對從 UI 獲取的 Roll 值乘以 `-1`，將純粹的數學旋轉轉換為符合操作直覺的視覺回饋，實現了前後端邏輯的解耦。
        4.  **修正 3-DOF 模型**：在 `kinematics.py` 中，重寫了三自由度平台的運動學計算函式，確保其旋轉是圍繞幾何中心（形心）進行的。                

*   **[新增]** **6.2 迭代修正二：狀態管理與初始化流程的根本性修復**
    *   **主題**：解決在點擊「新建專案」後，程式無法再次進行計算的嚴重迴歸錯誤。
        1.  **遇到的問題**：經過多次測試，發現問題根源在於應用程式的狀態管理混亂。點擊「新建專案」的流程，與使用者手動修改參數的流程之間存在邏輯衝突，導致程式進入一個不可預測的、被污染的狀態。
        2.  **錯誤的根源 1 (職責不清)**：子元件 (`six_dof_widget.py`) 在參數被修改時，錯誤地承擔了「禁用按鈕」的職責，導致主視窗 (`main_window.py`) 無法在正確的時機重新啟用它們。
        3.  **錯誤的根源 2 (重置不全)**：「新建專案」的流程沒有徹底重置所有相關的 UI 元件（特別是 `AnalysisWidget`），導致舊的狀態殘留。
        4.  **錯誤的根源 3 (訊號鏈路中斷)**：在模組化重構過程中，按鈕的 `clicked` 訊號未能正確地從子元件傳遞到主視窗。
    *   **最終方案：確立單一、權威的狀態管理流程**：
        1.  **`on_new_project` 為唯一重置入口**：`main_window.py` 中的 `on_new_project` 被確立為唯一、權威的應用程式重置函式。任何需要重置專案的操作（點擊「新建專案」按鈕、切換平台類型）都必須呼叫此函式。此函式負責徹底重置**所有**後端引擎與**所有**相關 UI 元件（包括幾何參數面板和姿態控制面板）。
        2.  **`parameter_changed` 職責簡化**：子元件中的 `_on_parameter_changed` 函式被重構。其**唯一**職責是發射 `parameter_changed` 訊號。
        3.  **`_mark_as_dirty` 職責釐清**：`main_window.py` 中的 `_mark_as_dirty` 函式現在是處理 `parameter_changed` 訊號的**唯一**插槽。其**唯一**職責是將 `is_dirty` 旗標設為 `True`，並呼叫子元件的 `reset_all_calculated_values()` 來清除過期的計算結果並禁用後續按鈕。
        4.  **`on_parameters_confirmed` 職責**：此函式在執行任何新計算之前，會先呼叫 `core_engine.reset_calculated_parameters()`，確保後端處於絕對乾淨的狀態，從而保證了計算的可靠性。

*   **[修改]** **6.3 渲染策略的演进**
    *   **主題**：解決 3D 動畫過程中的背景閃爍問題。
    *   **初期問題**：在動畫的每一幀都呼叫 `plotter.clear()`，導致靜態的座標軸背景不斷閃爍，視覺體驗不佳。
    *   **最終方案**：採用「原地更新 (Update-in-Place)」策略。重量級的 `rebuild_scene()` 函式只在需要徹底刷新時（如讀取專案）呼叫，它負責建立所有演員 (Actor)。而輕量級的 `update_platform_pose()` 函式則在動畫和滑塊拖動時高頻呼叫，它**絕不清除場景**，而是透過 `actor.mapper.dataset.copy_from()` 這個高效的 API，只更新模型的頂點數據，從而根除了閃爍問題。

*   **[修改]** **6.4 3D 視窗 UI 整合的挑戰**
    *   **主題**：為 3D 視窗添加浮動的視角控制按鈕。
    *   **已棄用的方案**：曾嘗試將一個純 Qt 元件 (`ViewControlsWidget`) 作為 `PyVistaWidget` (`QtInteractor`) 的子元件。
    *   **遇到的問題**：該方案導致了 Qt 和 VTK 兩個渲染引擎之間的嚴重衝突，具體表現為：
        1.  終端機出現 `QWidget::paintEngine: Should no longer be called` 警告。
        2.  作為子元件的按鈕面板被 VTK 渲染層完全覆蓋而無法顯示。
        3.  `PyVistaWidget` 內部的事件處理循環被擾亂，導致互動式座標軸標記 (Gizmo) 無法響應點擊。
    *   **最終方案**：採用「**徹底解耦**」的策略。將所有視角控制按鈕**移至**主視窗 (`MainWindow`) 中進行管理。`MainWindow` 作為一個純 Qt 環境，可以穩定地建立和顯示按鈕。當按鈕被點擊時，`MainWindow` 再向 `PyVistaWidget` 發出單向的、清晰的指令來改變視角。這個方案徹底避免了渲染衝突，並使得各模組的職責更加單一和清晰。

*   **[修改]** **6.5 API 使用的穩健性**
    *   **主題**：確保程式在不同版本的 PyVista 函式庫下都能穩定運行。
    *   **遇到的問題**：
        1.  初期程式碼直接存取了 `camera.view_up` 或 `actor.copy_from` 等底層或特定版本的 API，導致了在某些環境下出現 `AttributeError` 和 `ValueError`。
        2.  使用了在舊版本中不存在的 `remove_actor(..., on_missing='ignore')` 參數，導致了 `TypeError`。
    *   **最終方案**：
        1.  轉而使用 PyVista 提供的高階、穩健的 API。例如，使用 `plotter.camera_position` 來一次性處理視角的方位，使用 `actor.mapper.dataset` 來更新模型數據。
        2.  放棄對特定版本功能的依賴，改用更具普適性的「手動檢查」邏輯（在移除演員前，先檢查其是否存在），確保了程式的向後相容性。
