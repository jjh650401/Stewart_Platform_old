### **應用程式開發指南：模組化史都華平台設計與模擬工具**

**版本：1.7 (穩定版)**
**日期：2025年8月26日**

**目標：** 為遊樂設備行業的技術人員，打造一款基於 Python 的視窗版桌面應用程式，用於史都華平台 (Stewart Platform)（六自由度與三自由度）的參數化設計、性能分析、動態模擬與驗證。

**[開發者註記：版本變更日誌 (v1.6 -\> v1.7 穩定版)]**

  * **[核心重構] 四層架構導入**：為根除 v1.6 中存在的狀態管理混亂與多執行緒不穩定問題，v1.7 引入了全新的四層應用程式架構，對專案進行了根本性的重構，以實現職責分離與高內聚低耦合。
  * **[核心新增] 狀態管理層 (`StateManager`)**：新增 `StateManager` 類別，作為應用程式**唯一、權威的數據中心 (Single Source of Truth)**，集中管理所有持久化狀態。
  * **[核心新增] 高層分析層 (`AnalysisEngine`)**：新增 `AnalysisEngine` 類別，作為一個獨立的、執行緒安全的背景工作者，專門負責執行耗時的分析任務。
  * **[核心新增] 全域最大靜載分析功能**：基於 `AnalysisEngine`，實作了由 Grok (xAI) 文件指導的、**完全確定性**的「全域最大靜載分析」演算法，採用 **LHS+SQP** 混合策略，確保了分析的全面性與準確性。
  * **[核心修正] 多執行緒穩定性**：徹底修復了先前版本中因跨執行緒物件引用與生命週期管理不當而導致的 `QThread` 崩潰問題。採用了安全的「任務資料包」模式進行資料傳遞。
  * **[核心修正] 單位換算流程**：修復了 `CoreEngine` 與 `AnalysisEngine` 之間因「雙重換算」導致的角度單位（弧度/角度）混亂問題，確保了分析演算法能在正確的物理邊界內進行採樣。
  * **[修改] 職責簡化**：`MainWindow` 的職責被大幅簡化，回歸其作為 UI 總管與事件協調器的核心角色。`CoreEngine` 的職責也更聚焦於純粹的運動學求解。
  * **[新增] 開發歷程記錄**：在第六章中，詳細記錄了 v1.7 開發分支從遇到多執行緒崩潰，到歷經數次除錯與重構，最終達成穩定狀態的全過程，為未來開發提供寶貴經驗。

#### **1.2 虛擬環境建置**

使用虛擬環境可以隔離專案依賴，避免與系統全域套件衝突。

1.  **開啟終端**: 在 VS Code 中，點擊 `Terminal` \> `New Terminal`。
2.  **確認路徑**: 確保終端機的路徑在 `D:\Python_Programs\Stewart_Platform`。
3.  **建立虛擬環境**: 執行以下指令，建立名為 `.venv` 的虛擬環境。
    ```bash
    python -m venv .venv
    ```
4.  **啟動虛擬環境**:
    ```bash
    .\.venv\Scripts\activate
    ```
    啟動成功後，終端機提示符前會出現 `(.venv)` 字樣。
5.  **(可選) 選擇直譯器**: VS Code 可能會自動偵測到虛擬環境。如果沒有，手動點擊右下角的 Python 版本，選擇 `.venv` 中的 Python 直譯器。

1.  在專案根目錄下建立 `requirements.txt` 檔案，並填入以下內容：
    ```text
    numpy
    scipy
    PyQt6
    pybullet
    reportlab

    pyvistaqt
    ```
2.  在已啟動虛擬環境的終端機中，執行以下指令來安裝所有必要的套件：
    ```bash
    python -m pip install --upgrade pip
    pip install -r requirements.txt
    ```

### **第二章：核心理念與技術棧**

#### **2.1 核心理念**

  * **[修改] 模組化與職責分離**: **(v1.7 核心升級)** 應用程式採用嚴格的四層架構，將狀態管理、核心計算、高層分析與使用者介面徹底解耦，確保了程式碼的高內聚、低耦合，便於獨立測試、維護與未來擴展。
  * **引導式計算**: 程式應作為設計夥伴，能理解參數間的依賴關係，在資料不完整時引導使用者補全，並自動推算可衍生的參數。

  * **中央化設定**：將所有可調整的預設值、樣式和演算法參數集中到單一的設定檔 (`config.py`) 中，實現設定與程式碼的分離，便於快速微調與維護。
  * **使用者狀態追蹤**：應用程式應能追蹤使用者的修改狀態，並在關閉前主動提示儲存未保存的變更，確保工作不會意外遺失。

### **第三章：變數與參數定義**

本章定義了應用程式中使用的所有關鍵變數，作為唯一的參考標準。

  * **GUI 與核心引擎單位約定**:
      * **GUI 層**: 為了符合使用者習慣，所有在圖形介面 (`GeometryWidget`, `DynamicsWidget`) 的輸入框中，長度單位皆為 **毫米 (mm)**。
      * **核心引擎層 (`CoreEngine`)**: 為了符合科學計算標準，所有內部計算與參數儲存，長度單位皆為 **米 (m)**。
      * **資料流**: GUI 層在將參數傳遞給核心引擎前，負責將 `mm` 轉換為 `m`。核心引擎回傳計算結果時，GUI 層負責將 `m` 轉換回 `mm` 進行顯示。
      * **[新增]** **加速度單位**: GUI 層為了方便使用者輸入，線性加速度單位使用**重力加速度 (g)**。在將參數傳遞給核心引擎前，GUI 層負責將 `g` 值乘以 `9.81` 轉換為核心引擎所使用的 `m/s²` 單位。
  * **幾何參數**:
      * $R\_a$ (m): 下平台節點圓的半徑。
      * $R\_b$ (m): 上平台節點圓的半徑。
      * **[修改]** $H$ (m): **自然平衡零位高度 (Natural Balance Zero Position Height)**。此為一個**計算結果**，定義為當所有電動缸長度均處於其**可用行程中點** ($L + s\_{buffer}/2 + s/2$) 時，平台在保持水平姿態下的高度。它是所有姿態控制和工作空間分析的**操作基準零點**。
      * **[修改]** $h$ (m): **平台初始高度 (Initial Height)**。此為一個理論上的物理量，定義為當所有電動缸長度均處於其**最小機械長度** ($L$) 時，平台在保持水平姿態下的高度。它代表了平台的**物理下限**，對應總機械行程的起點。
      * **[新增]** **開發者註記：`H` 與 `h` 的區別**
        > `H` 是軟體中所有相對運動的**參考原點**，旨在最大化和對稱化可用工作空間。而 `h` 則代表平台的**物理最低點**。兩者在概念上和數值上均不相同，請務必加以區分。
      * **自然零位偏移** $(T\_{x0}, T\_{y0})$ (m): 與 $H$ 同時解算出的，在自然平衡零位下的水平面偏移量。
      * **六自由度平台**:
          * $D\_f$ (m): 下平台相鄰節點間的較大弦長。
          * $d\_f$ (m): 下平台相鄰節點間的較小弦長。
          * $D\_m$ (m): 上平台相鄰節點間的較大弦長。
          * $d\_m$ (m): 上平台相鄰節點間的較小弦長。
      * **[新增]** **相位角** $\\Delta\\theta$ (rad 或 deg): **相位角 (Phase Angle)**，亦可稱為 **交錯角 (Stagger Angle)** 或 **扭轉角 (Twist Angle)**。
          * **定義**: 在平台的初始零位姿態下，從 Z 軸俯視，上平台節點 $B\_i$ 的方位角與下平台對應節點 $A\_i$ 的方位角之間的夾角。
          * **性質**: 這是一個由上下平台四個弦長 ($D\_f, d\_f, D\_m, d\_m$) 決定的**內建幾何特性**，而非可動的姿態參數。
          * **意義**: 此參數對於**避免奇異點 (Singularity)**、**優化工作空間形狀**以及改善力傳遞特性至關重要。
  * **電動缸參數**:
      * $L$ (m): 電動缸的固定最小長度。
      * $s$ (m): 電動缸的**可用行程 (Usable Stroke)** (使用者**輸入**)。
      * $s\_{buffer}$ (m): 電動缸兩端預留的**安全裕量 (Safety Buffer)** 總和 (使用者**輸入**)。
      * $s\_{mech}$ (m): 電動缸的**總機械行程 (Total Mechanical Stroke)** (由程式**計算**，$s\_{mech} = s + s\_{buffer}$)。
      * $l\_i$ (m): 第 $i$ 根電動缸的當前長度。其安全運動範圍為 $[L + s\_{buffer}/2, L + s\_{buffer}/2 + s]$。
  * **視角參數 (View Parameters)**:
      * `view_params` (dict): 一個包含攝影機所有狀態的字典集合，用於儲存和恢復 3D 視圖。
      * `cpos` (list): 一個列表，包含三個核心向量 `[position, focal_point, view_up]`，定義了攝影機的方位。
      * `parallel_scale` (float): 一個數值，定義了攝影機的縮放等級或遠近。
  * **平台自由度與性能**:
      * $T\_x, T\_y, T\_z$ (m): 沿 X, Y, Z 軸的最大平移範圍。
      * $\\alpha, \\beta, \\gamma$ (rad 或 deg): 繞 X, Y, Z 軸的最大旋轉範圍 (Roll, Pitch, Yaw)。
      * $v\_{max}, a\_{max}$ (m/s, m/s²): 平台的最大線速度與線加速度。
  * **驅動系統參數**:
      * $P\_h$ (m/rev): 螺桿導程 (Pitch)。
      * $N\_1$: 傳動端（馬達端）皮帶輪的齒數。
      * $N\_2$: 從動端（螺桿端）皮帶輪的齒數。
      * $i$: 減速比，$i = N\_2 / N\_1$。
      * $\\eta\_s$: 螺桿傳動效率。
      * $\\eta\_b$: 皮帶輪傳動效率。
      * $F\_{rated}$ (N): 每根電動缸的額定最大軸向出力。
      * $\\tau\_{motor}$ (N·m): 馬達的額定扭力。
      * $n\_{motor}$ (rev/s): 馬達的額定轉速。
  * **[修改]動力學參數**:
      * `platform_mass` (kg): 上平台本身的質量。
      * `load_mass` (kg): 附加於上平台的負載質量。
      * `load_com_x`, `load_com_y`, `load_com_z` (m): 負載質心 (Center of Mass) 相對於上平台幾何中心的位置向量。
      * `lin_accel` (m/s²): 平台期望的線性加速度 (Linear Acceleration) 向量 `[ax, ay, az]`。
      * `ang_accel` (rad/s²): 平台期望的角加速度 (Angular Acceleration) 向量 `[αx, αy, αz]`。
      * $\\mathbf{I}$ (kg·m²): 平台與負載的轉動慣量張量。
      * $g$ (m/s²): 重力加速度，預設為 9.81。

### **第四章：核心計算公式**

本章節明確定義了將幾何參數轉換為數學模型所需的公式。

#### **4.1 節點座標與連接定義**

  * **基準座標系與標準方位**

      * **原點**: `(0, 0, 0)` 固定於**下平台**的幾何中心。
      * **座標軸**: 採用右手座標系。`+X` 軸水平向右，`+Y` 軸水平向前，`+Z` 軸垂直向上。
      * **標準初始方位**: 所有平台的初始方位定義，皆以此座標系為基準。下平台的標準方位如下圖所示，此為所有運動學與視覺化呈現的唯一標準。

  * **平台方位示意圖**

      * **六自由度平台 (俯視圖)**:

          * 平台沿 **Y 軸**鏡像對稱。
          * `A1-A6` 弦平行於 X 軸，位於 Y 軸負方向。
          * 節點從右下角 `A1` 開始，**逆時針**編號。

      * **三自由度平台 (俯視圖)**:

          * 平台沿 **Y 軸**鏡像對稱。
          * `A3` 節點位於 Y 軸正向頂點。
          * `A1-A5` 底邊平行於 X 軸，位於 Y 軸負方向。

  * **4.1.1 自由度定義** 本節定義**上平台**相對於**下平台**的運動。所有旋轉均符合右手定則，但前端控制邏輯會進行調整以符合操作直覺。

      * **平移動作 (Translation)**:
          * **Surge (X)**: 沿 X 軸的左右運動。`+X` 為向**右**。
          * **Sway (Y)**: 沿 Y 軸的前後運動。`+Y` 為向**前**。
          * **Heave (Z)**: 沿 Z 軸的垂直運動。`+Z` 為**上升**。
      * **轉動動作 (Rotation)**:
          * **Pitch (俯仰)**: 繞 **X 軸** (橫軸) 旋轉。**操作定義**：增加 Pitch 值，平台**前端 (Y+) 抬起**。
          * **Roll (滾轉)**: 繞 **Y 軸** (縱軸) 旋轉。**操作定義**：增加 Roll 值，平台**右側 (X+) 下壓**。
          * **Yaw (偏航)**: 繞 **Z 軸** (垂直軸) 旋轉。**操作定義**：增加 Yaw 值，從上方俯視，平台進行**逆時針**旋轉。
      * **三自由度平台的自由度**: 包含 **Heave**, **Pitch**, **Roll**。

  * **開發者註記 (程式碼同步)**:

      * `kinematics.py` 中的 `_get_canonical_nodes` 函式是平台幾何的唯一真實來源。
      * 其內部的 `stagger_offset` 變數是**相位角 $\\Delta\\theta$ (Phase Angle)** 的直接程式碼實現，它根據弦長計算得出，並產生了上下平台之間關鍵的幾何扭轉。
      * `rotation_offset` 邏輯已被修正，以達成**本章節 4.1 所定義的標準初始方位**。

#### **4.2 運動學與動力學公式**

1.  **向量定義**:  
    $\\mathbf{l}\_i = (\\mathbf{T} + \\mathbf{R}\\mathbf{B}\_i^0) - \\mathbf{A}\_i$

2.  **逆向運動學 (Inverse Kinematics, IK)**:  
    $l\_i = ||(\\mathbf{T} + \\mathbf{R}\\mathbf{B}\_i^0) - \\mathbf{A}\_i||$

3.  **正向運動學 (Forward Kinematics, FK)**:  
    求解 $||\\mathbf{l}*i||^2 - l*{i, \\text{given}}^2 = 0$

4.  **逆動力學 (Inverse Dynamics)**:

      * **目標**: 求解各致動器 (電動缸) 所需的瞬時力 $F\_{actuators}$。
      * **核心方程式**:  
        $F\_{actuators} = (\\mathbf{J}^{-1})^T \\cdot \\mathbf{W}\_{ext}$
      * 其中 $\\mathbf{J}$ 是平台的**雅可比矩陣 (Jacobian Matrix)**，$\\mathbf{W}\_{ext}$ 是施加在平台的總外力/力矩向量 **(Wrench)**，它由重力與慣性力/力矩組成。
      * **開發者註記**:  
        `dynamics_engine.py` 中的模型為簡化模型，主要考慮重力與達朗貝爾慣性力，暫未包含高速旋轉下顯著的科里奧利力與向心力。  
        **此外，目前的轉動慣量張量 ($\\mathbf{I}$) 採用了一個固定的近似值 (`np.eye(3) * 0.1`)，並未根據平台和負載的實際幾何進行計算，此設計會影響高速轉動下的力矩計算精度，為未來版本的待改進項。**

### **第五章：應用程式模組化架構**

`[開發者註記：本章節已根據 v1.7 的四層架構重構進行了全面重寫]`

#### **[新增] 5.1 層次一：狀態管理層 (`state_manager.py`)**

  * **角色**: `StateManager` 類別，是應用程式**唯一、權威的數據中心 (Single Source of Truth)**。
  * **職責**:
    1.  **集中管理**: 負責儲存所有需要跨模組共享或需要持久化的應用程式狀態，如專案路徑、工作空間分析結果（可用與機械）、當前平台類型、`is_dirty` 標記等。
    2.  **狀態接口**: 提供統一的 `get/set` 接口供其他模組讀取或更新狀態，避免狀態數據散落在各個 UI 元件中。
    3.  **生命週期**: 其生命週期與主視窗相同，確保在整個應用程式運行期間，狀態都是一致且可追溯的。

#### **[修改] 5.2 層次二：核心計算層**

  * **1. 運動學核心 (`kinematics.py`)**

      * **角色**: `CoreEngine` 類別，專注於**純粹的運動學與幾何求解**。
      * **職責**:
        1.  **無狀態計算**: 作為一個計算工具，它本身不儲存高層次的應用程式狀態（如工作空間結果）。它接收基礎參數，執行計算，然後立即回傳結果。
        2.  **運動學求解器**: 封裝所有核心數學運算，包括逆向運動學、幾何求解、以及基於 `SLSQP` 最佳化的工作空間邊界分析。
        3.  **姿態驗證**: 提供 `is_pose_valid` 接口，用於快速檢查一個給定的姿態是否在指定的行程限制內物理可達。
        4.  **檔案處理**: 負責將專案的所有參數序列化至 JSON 檔案或從中讀取。

  * **2. 動力學核心 (`dynamics_engine.py`)**

      * **角色**: `DynamicsEngine` 類別，專注於底層的**逆動力學計算**。
      * **職責**:
          * 接收平台的瞬時幾何狀態與運動參數（加速度）。
          * 建立平台的雅可比矩陣，並求解出各致動器所需的瞬時出力。

#### **[新增] 5.3 層次三：高層分析層 (`analysis_engine.py`)**

  * **角色**: `AnalysisEngine` 類別，一個**獨立的、執行緒安全的背景工作者**。
  * **職責**:
    1.  **執行複雜任務**: 專門負責執行如「全域最大靜載分析」這類計算密集、耗時長的分析任務，避免主 UI 執行緒被阻塞。
    2.  **LHS+SQP 演算法**: 內部實作了基於拉丁超立方採樣與序列二次規劃的混合智慧演算法，用於在整個工作空間內尋找極值點。
    3.  **執行緒安全**: 被設計為一個無狀態的物件。它不直接存取任何主執行緒的物件，而是透過一個「任務資料包」接收工作所需的所有數據，並透過 PyQt 的信號與槽機制 (`pyqtSignal`) 安全地將進度與結果回傳給主視窗。

#### **[修改] 5.4 層次四：使用者介面與協調層 (GUI)**

  * **1. 主視窗 (`main_window.py`)**

      * **角色**: `MainWindow` 類別，應用程式的**UI 總管**與**事件協調中心**。
      * **職責**:
        1.  **UI 組合**: 建立並管理所有 UI 元件的佈局與顯示。
        2.  **事件協調**: 這是其核心職責。它負責接收來自 UI 元件的訊號（如按鈕點擊），然後決定呼叫哪個後端模組來處理該事件。
        3.  **資料流控制**: 負責在各個層次之間傳遞資料。例如，從 `CoreEngine` 獲取計算結果，一份儲存到 `StateManager`，另一份轉換單位後傳遞給 `AnalysisWidget` 顯示。
        4.  **執行緒管理**: 負責創建、啟動和安全地清理 `AnalysisEngine` 的背景執行緒。在啟動前，它會從 `StateManager` 和 `CoreEngine` 收集數據，打包成「任務資料包」後再派發給背景執行緒。

  * **2. 各功能面板 (`controls/` 目錄下的元件)**

      * **角色**: 專用的 UI 元件，負責特定功能的「顯示」與「使用者輸入」。
      * **職責**: 每個 Widget（如 `DynamicsWidget`, `AnalysisWidget`）都像一個儀表板。它們的職責是：接收 `MainWindow` 傳來的數據並顯示；監聽使用者的操作（如拖動滑塊），並將這些操作以 `pyqtSignal` 的形式發射出去，通知 `MainWindow` 進行處理。它們自身不包含複雜的應用程式邏輯。

### **第六章：開發者註記與決策記錄**

本章旨在記錄在達成各穩定基線的過程中，所遇到的關鍵挑戰、錯誤分析以及最終的解決方案。這份記錄是未來維護與功能迭代的寶貴資產，旨在避免重蹈覆轍。

  * **6.1 迭代修正一：物理模型與方位定義的標準化**

      * **主題**：確保軟體的計算、顯示與物理現實完全一致。
      * **遇到的问题与决策记录**：
        1.  **行程定義偏差**：初版對「可用行程」的定義忽略了 `s_buffer`，導致工作空間分析不準確。
        2.  **方位定義顛倒**：初版六自由度平台的初始方位與設計示意圖顛倒 180 度，是導致旋轉方向混亂的根源。
        3.  **旋转直觉不符**：在方位修正後，純數學的「右手定則」旋轉方向與模擬器操作員的直覺（如 `+Pitch`=抬頭）不符。
        4.  **3-DOF 旋转模型错误**：初版三自由度平台的旋轉是圍繞「外接圓圓心」而非「幾何中心」，導致動作異常。
      * **最終方案：**：
        1.  **明確物理模型**：在第三章中，以圖文方式明確電動缸行程的物理分佈，並以此為基准，重寫了 `kinematics.py` 中所有相關的計算邏輯（`H` 高度，工作空間分析）。
        2.  **強制標準方位**：在 `kinematics.py` 中，透過增加 180 度旋轉偏移，強制使六自由度平台的初始方位與第四章新增的「標準方位示意圖」對齊。
        3.  **前端體驗適配**：在 `main_window.py` 的 `update_3d_view` 函式中，對從 UI 獲取的 Roll 值乘以 `-1`，將純粹的數學旋轉轉換為符合操作直覺的視覺回饋，實現了前後端邏輯的解耦。
        4.  **修正 3-DOF 模型**：在 `kinematics.py` 中，重寫了三自由度平台的運動學計算函式，確保其旋轉是圍繞幾何中心（形心）進行的。

  * **6.2 迭代修正二：狀態管理與初始化流程的根本性修復**

      * **主題**：解決在點擊「新建專案」後，程式無法再次進行計算的嚴重迴歸錯誤。
        1.  **遇到的問題**：經過多次測試，發現問題根源在於應用程式的狀態管理混亂。點擊「新建專案」的流程，與使用者手動修改參數的流程之間存在邏輯衝突，導致程式進入一個不可預測的、被污染的狀態。
        2.  **錯誤的根源 1 (職責不清)**：子元件 (`six_dof_widget.py`) 在參數被修改時，錯誤地承擔了「禁用按鈕」的職責，導致主視窗 (`main_window.py`) 無法在正確的時機重新啟用它們。
        3.  **錯誤的根源 2 (重置不全)**：「新建專案」的流程沒有徹底重置所有相關的 UI 元件（特別是 `AnalysisWidget`），導致舊的狀態殘留。
        4.  **錯誤的根源 3 (訊號鏈路中斷)**：在模組化重構過程中，按鈕的 `clicked` 訊號未能正確地從子元件傳遞到主視窗。
      * **最終方案：確立單一、權威的狀態管理流程**：
        1.  **`on_new_project` 為唯一重置入口**：`main_window.py` 中的 `on_new_project` 被確立為唯一、權威的應用程式重置函式。任何需要重置專案的操作（點擊「新建專案」按鈕、切換平台類型）都必須呼叫此函式。此函式負責徹底重置**所有**後端引擎與**所有**相關 UI 元件（包括幾何參數面板和姿態控制面板）。
        2.  **`parameter_changed` 職責簡化**：子元件中的 `_on_parameter_changed` 函式被重構。其**唯一**職責是發射 `parameter_changed` 訊號。
        3.  **`_mark_as_dirty` 職責釐清**：`main_window.py` 中的 `_mark_as_dirty` 函式現在是處理 `parameter_changed` 訊號的**唯一**插槽。其**唯一**職責是將 `is_dirty` 旗標設為 `True`，並呼叫子元件的 `reset_all_calculated_values()` 來清除過期的計算結果並禁用後續按鈕。
        4.  **`on_parameters_confirmed` 職責**：此函式在執行任何新計算之前，會先呼叫 `core_engine.reset_calculated_parameters()`，確保後端處於絕對乾淨的狀態，從而保證了計算的可靠性。

  * **6.3 渲染策略的演进**

      * **主題**：解決 3D 動畫過程中的背景閃爍問題。
      * **初期問題**：在動畫的每一幀都呼叫 `plotter.clear()`，導致靜態的座標軸背景不斷閃爍，視覺體驗不佳。
      * **最終方案**：採用「原地更新 (Update-in-Place)」策略。重量級的 `rebuild_scene()` 函式只在需要徹底刷新時（如讀取專案）呼叫，它負責建立所有演員 (Actor)。而輕量級的 `update_platform_pose()` 函式則在動畫和滑塊拖動時高頻呼叫，它**絕不清除場景**，而是透過 `actor.mapper.dataset.copy_from()` 這個高效的 API，只更新模型的頂點數據，從而根除了閃爍問題。

  * **6.4 3D 視窗 UI 整合的挑戰**

      * **主題**：為 3D 視窗添加浮動的視角控制按鈕。
      * **已棄用的方案**：曾嘗試將一個純 Qt 元件 (`ViewControlsWidget`) 作為 `PyVistaWidget` (`QtInteractor`) 的子元件。
      * **遇到的問題**：該方案導致了 Qt 和 VTK 兩個渲染引擎之間的嚴重衝突，具體表現為：
        1.  終端機出現 `QWidget::paintEngine: Should no longer be called` 警告。
        2.  作為子元件的按鈕面板被 VTK 渲染層完全覆蓋而無法顯示。
        3.  `PyVistaWidget` 內部的事件處理循環被擾亂，導致互動式座標軸標記 (Gizmo) 無法響應點擊。
      * **最終方案**：採用「**徹底解耦**」的策略。將所有視角控制按鈕**移至**主視窗 (`MainWindow`) 中進行管理。`MainWindow` 作為一個純 Qt 環境，可以穩定地建立和顯示按鈕。當按鈕被點擊時，`MainWindow` 再向 `PyVistaWidget` 發出單向的、清晰的指令來改變視角。這個方案徹底避免了渲染衝突，並使得各模組的職責更加單一和清晰。

  * **6.5 API 使用的穩健性**

      * **主題**：確保程式在不同版本的 PyVista 函式庫下都能穩定運行。
      * **遇到的問題**：
        1.  初期程式碼直接存取了 `camera.view_up` 或 `actor.copy_from` 等底層或特定版本的 API，導致了在某些環境下出現 `AttributeError` 和 `ValueError`。
        2.  使用了在舊版本中不存在的 `remove_actor(..., on_missing='ignore')` 參數，導致了 `TypeError`。
      * **最終方案**：
        1.  轉而使用 PyVista 提供的高階、穩健的 API。例如，使用 `plotter.camera_position` 來一次性處理視角的方位，使用 `actor.mapper.dataset` 來更新模型數據。
        2.  放棄對特定版本功能的依賴，改用更具普適性的「手動檢查」邏輯（在移除演員前，先檢查其是否存在），確保了程式的向後相容性。

  * **[新增]** **6.6 迭代修正三：v1.7 多執行緒穩定性重構**

      * **主題**：解決在點擊「分析全域最大靜載」後，程式因多執行緒問題而卡死或崩潰的根本性錯誤。
      * **遇到的问题与决策记录**：
        1.  **初步診斷 (`AttributeError`)**：初次崩潰來自於 `MainWindow` 呼叫了 `CoreEngine` 中一個不存在的方法 (`reset_calculated_parameters`)。雖然補上該方法能解決直接崩潰，但這揭示了更深層次的狀態管理問題：**誰應該在何時重置何種狀態？**
        2.  **二次診斷 (單位換算錯誤)**：解決 `AttributeError` 後，分析依然失敗，並提示「未能找到任何有效姿態點」。經追蹤發現，`CoreEngine` 在回傳工作空間時**錯誤地**將弧度轉為角度，而 `AnalysisEngine` 又**再次**進行了轉換，導致採樣範圍被放大了數千倍，所有採樣點均無效。
        3.  **最終診斷 (`QThread Destroyed`)**：修正單位問題後，分析終於可以運行，但在完成的瞬間，程式以 `QThread: Destroyed while thread is still running` 的錯誤崩潰。根本原因在於 `MainWindow` 的**物件生命週期管理不當**：它在收到 `analysis_finished` 訊號後，過早地將 `self.analysis_thread` 設為 `None`，導致背景執行緒在其標準退出流程完成前就被強制銷毀。
      * **最終方案：確立 v1.7 的四層架構與安全執行緒模型**：
        1.  **引入 `StateManager`**：為了解決狀態混亂問題，引入 `StateManager` 作為唯一數據中心。`CoreEngine` 不再儲存工作空間等高層次狀態。
        2.  **嚴格單位劃分**：確立了「**後端統一用弧度，前端協調器負責轉角度**」的原則。`CoreEngine` 只回傳純淨的弧度值；`MainWindow` 接收後，一份存入 `StateManager`，另一份複製轉換後再送往 UI 顯示。
        3.  **執行緒安全重構**：
              * 將 `AnalysisEngine` 改造為**完全無狀態**的獨立工作者，其 `__init__` 不接收任何主執行緒物件。
              * `MainWindow` 採用「**任務資料包**」模式，在啟動執行緒前打包好所有數據，透過 `lambda` 函式安全地傳遞給 `AnalysisEngine`。
              * `MainWindow` 採用**基於 `finished` 訊號的清理機制**，確保只有在 `QThread` 完全結束其生命週期後，才安全地釋放對其物件的引用，徹底根除了崩潰問題。
